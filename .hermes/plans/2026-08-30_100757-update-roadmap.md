# Update `docs/ROADMAP.md` without eating context

> **For Hermes:** Do **not** use subagent-driven-development (too much review overhead for a single markdown rewrite). Use the **bounded parallel auditors** in Task 2, then one parent write. Do **not** implement until the user says go.

**Goal:** Replace the 644-line stale ROADMAP with a ~150–220 line living backlog that only lists work that is still open, and points at existing topic docs instead of duplicating them.

**Architecture:** Treat ROADMAP as a **claim list**, not a docs-sync of 86 files. Never ingest `docs/` (ignore `docs/archive/` always). Parent keeps ROADMAP + this plan + auditor verdicts. Children each see 1 ROADMAP slice + 1–3 hub files (headings / Open lists only) and return a 10-line table. Then parent `write_file`s the new ROADMAP in one shot.

**Tech stack:** markdown only. No code, no tests, no `make typecheck`.

## How to run a docs task this size in general

This ROADMAP pass is the template for any “the docs are huge, update X”:

1. **Name the source of truth.** ROADMAP is not the source of truth for shipped features (`features.md`) or for architecture (`repo-map.md` / topic hubs). It is only the backlog. Updating it does not require reading hubs in full.
2. **Inventory filenames, not contents.** `find` + `rg '^#'` + existence probes.
3. **Ignore archive** unless a live link 404s.
4. **Slice claims, not directories.** One child per *question* (“is mail merge still a gap?”), not per folder.
5. **Cap what returns to the parent.** Verdict tables, never raw docs.
6. **Rewrite the small file once.** Do not patch-in-place a 644-line file that is 50% delete.
7. **Refuse drive-by work.** Do not “also” refresh monaco/eval/grammar plans.

That is how 86 files stay out of context and the job still finishes.
